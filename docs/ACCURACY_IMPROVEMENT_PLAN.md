# Способы повышения точности JT-Zero Optical Flow / EKF

## Текущий baseline

Рабочий контур:

```text
OV9281 → OPTICAL_FLOW
TF-Luna → масштаб OF + RangeFinder
Compass → yaw
ArduPilot EKF3 → итоговая XY/Z
```

По bench-тестам текущая итоговая ошибка замыкания EKF по XY обычно находится в диапазоне десятков миллиметров. Комбинированный ручной тест дал около 48 мм после горизонтального удаления примерно до 0.8 м, изменения высоты примерно на 0.4 м и одновременных изменений attitude.

Цель дальнейшей работы — уменьшить систематические ошибки измерения, прежде всего утечку rotation/scale в translation, не разрушая рабочий baseline.

## Статус после проверки компенсации вращения (2026-09-15)

Экспериментальная ветка `rotation-comp-v2` проверила три варианта:

- **Lever-arm `ω × r` — принят в production.** При повторных YAW-прогонах уменьшил ложный optical flow примерно на 40–48%, а обычный поступательный regression-прогон после включения компенсации прошёл без деградации baseline. Используется физически измеренная геометрия камеры из `config/mount_geometry.json`; эмпирические множители и подгонка `FLOW_POS` не применяются.
- **Компенсация через ΔR — отклонена.** В проверенных прогонах дала существенно меньший эффект и не используется в production.
- **Frame-aligned lever — отклонён.** Online-валидность во время YAW оказалась недостаточной; путь удалён из активного кода.
- Исходные V4L2 timestamps подтверждены как `CLOCK_MONOTONIC`; их логирование оставлено как полезная временная телеметрия, но отдельная timing-ветка исследований закрыта.

Текущий рабочий путь:

```text
OV9281 raw OF
      ↓
lever-arm compensation: v_cam(rotation) = ω × r
      ↓
flow_send_x/y
      ↓
OPTICAL_FLOW → ArduPilot EKF3
```

При невозможности вычислить lever-arm компенсацию runtime автоматически отправляет прежний raw OF, поэтому потеря gyro/range не блокирует поток.

## Статус feature-estimator экспериментов (2026-09-15)

После production lever-arm отдельно проверены следующие способы на Raspberry Pi:

- **Global-quality + spatial-cap feature grid — отклонён.** По сравнению с текущим production 3×3 per-cell GFTT уменьшились средние features/inliers, ухудшилась пространственная заполненность, а GFTT стал примерно в 3.5 раза дороже. Текущий per-cell grid остаётся production baseline.
- **Forward-backward LK ≤ 1 px — отклонён для постоянного production.** В синхронном A/B/C/D прогоне FB прошло около 97.9% tracks; после уже существующего RANSAC отличие составило примерно два inlier на кадр, тогда как дополнительный FB проход стоил около 22–23 ms/кадр.
- **FB + adaptive Huber IRLS — не принят.** На тех же кадрах доказанного улучшения покоя/OF относительно production не получено.
- **FB + structure-tensor observability weighting — не принят.** Изменения относительно production малы и не дают практического выигрыша.
- Shadow-код A/B/C/D сохранён для специальных диагностических запусков через `MONKEYS_FB_SHADOW_MAX_PX`, но в обычном Web runtime он выключен и не расходует CPU.

Практический вывод: текущие correspondences уже имеют высокий RANSAC/FB consistency, поэтому следующий приоритет — не усложнение GFTT/LK/RANSAC, а качество/uncertainty публикуемого Optical Flow и его использования EKF.

## Рекомендуемая архитектура V2

Пункты 1–6 следует рассматривать не как шесть независимых экспериментов, а как одну последовательную архитектуру измерителя:

```text
camera frame t0                camera frame t1
      │                              │
      ├──── attitude(t0)             ├──── attitude(t1)
      │                              │
      └──────────────┬───────────────┘
                     ▼
               точный ΔR
                     │
                     ▼
        rotation каждого camera ray
                     │
observed LK flow ────┤
                     ▼
           remove known rotation
                     │
                     ▼
            robust translation
                     │
            spatial distribution
                     │
                     ▼
             OF measurement
                     │
          quality / uncertainty
                     │
                     ▼
              ArduPilot EKF
```

### 1. Компенсация rotation через относительный поворот

Вместо одновременной визуальной оценки translation и rotation использовать независимую ориентацию FC.

Для двух кадров вычислять относительный поворот камеры:

```text
R_C1_C2 = R_BCᵀ · R_B1_B2 · R_BC
```

Для feature предыдущего кадра:

```text
ray1 = K⁻¹ [u, v, 1]
ray2_rot = R_C1_C2 · ray1
```

После проекции `ray2_rot` обратно в изображение получается ожидаемое движение feature только от вращения. Его следует удалить из наблюдаемого LK flow до оценки translation.

Преимущество: одновременно учитываются yaw, pitch, roll, перспектива и фактическая ориентация OV9281.

### 2. Точная привязка attitude к timestamps кадров

Не использовать просто ближайший или последний gyro/attitude sample. Требуются ориентации, интерполированные на времена обоих кадров:

```text
q0 = attitude(t_frame0)
q1 = attitude(t_frame1)
ΔR = q1 · inverse(q0)
```

Это особенно важно при высокой угловой скорости.

### 3. Robust translation

После удаления известного rotational flow оценивать translation устойчивым методом. Возможные критерии отбраковки/взвешивания:

- LK residual;
- forward-backward error;
- RANSAC consistency;
- длина истории track;
- согласованность с соседними tracks;
- положение feature в кадре.

### 4. Spatial distribution

Features должны покрывать изображение, а не концентрироваться в одном текстурированном участке. Практический вариант — разделить рабочую область кадра на сетку и поддерживать минимальное/максимальное число tracks в каждой ячейке.

Это уменьшает утечку scale и rotation в translation при несимметричной текстуре.

### 5. Persistent tracks

Стабильный feature, существующий много кадров и имеющий малый residual, должен иметь больший вес, чем только что созданная точка или нестабильный track.

### 6. Динамический quality

Качество OPTICAL_FLOW должно отражать фактическое состояние измерения:

```text
quality = f(
    track_count,
    inlier_ratio,
    LK_error,
    spatial_coverage,
    rotational_residual
)
```

При хорошем изображении и согласованных tracks EKF может сильнее доверять OF. При плохой текстуре, сильном residual или малом числе tracks — слабее.

### 7. Динамическая uncertainty/covariance

После появления достоверной оценки качества можно отдельно исследовать динамическую неопределённость ExternalNav/OF для EKF. Не следует начинать с этого до улучшения самого измерителя.

## Что сейчас не следует менять

Без новых независимых доказательств не менять одновременно с V2:

- `fx/fy`;
- `T_BS`;
- scale OF;
- TF-Luna offset;
- EKF source configuration;
- compass configuration;
- bench-takeoff pulse;
- deadband `vN/vE`;
- произвольные коэффициенты gyro compensation.

Текущий рабочий baseline необходимо сохранить для A/B-сравнения.

## Критерии принятия V2

V2 следует разрабатывать отдельно от рабочего baseline и принимать только по заранее определённым тестам.

Минимальный набор сравнения:

| Тест | Текущий baseline | Цель V2 |
|---|---:|---:|
| YAW около 90° | RAW порядка 100+ мм | **<30 мм RAW** |
| TILT около 25° | RAW порядка 90–100 мм | **<30 мм RAW** |
| Combined hand flight | EKF около 48 мм | **<30 мм EKF** |
| Линейное движение около 500 мм | Рабочий baseline | **Не ухудшить** |

Если V2 не даёт воспроизводимого улучшения относительно baseline, изменение не переносить в рабочий контур.

## Целевой ориентир

Текущие 20–50 мм EKF loop closure не следует считать фундаментальным пределом OV9281 + TF-Luna. Практическая следующая цель bench-этапа — получить устойчивые **10–30 мм EKF closure**, сохранив стабильность текущего рабочего контура.
